# 语音 · 多实例并发(GPT-SoVITS)—— 设计

状态:**暂停,不实现**。2026-09-24 实测 2 个实例的吞吐只有 1 个的 1.10 倍,没达到 1.3 倍的门槛(见「第一步:实测」的结果)。设计留着,以后换了模型或显卡再测
日期:2026-09-24
前置:语音功能本身的设计见 `2026-09-24-vn-voice-design.md`;5090 的环境、SSH、实测数据见 `docs/voice-server.md`

## 背景

用户实际玩下来有三点不满意:每条回复的第一句要等;翻得快就追上预合成;语气平、完全没有情绪变化。当天逐个查了原因。

### 情绪:问题在数据,代码不用改

库里阿米娅、琴柳各只有一行情绪「平静」。立绘表情对不上情绪名时用排第一的那行,所以每句都落到「平静」。GPT-SoVITS 的语气基本照搬参考音频,只有一段参考,每句就是一个调。「立绘表情 → 情绪 → 参考音频」这条链路本身是通的。

决定:继续用 GPT-SoVITS,从 PRTS 原声里给每个立绘表情补一段 5–10 秒的参考,情绪名(或别名)和立绘表情名一致;相近的表情用别名共用一段。这是 5090 那边的数据活,补完在插件页重新导入 `refs.json` 即可。两张卡现在的立绘表情(括号里是别名):

- 阿米娅:平静(normal)、微笑(smile)、开心(happy)、说话(talk)、认真(serious)、担心(worried)、难过(sad)、惊讶(surprised)、慌张(flustered、害羞)、红瞳(angry、生气)
- 琴柳:微笑(smile)、平静(normal、认真)、温柔(gentle)、开心(happy)、害羞(shy、脸红)、疑惑(confused)、惊讶(surprised)、担心(worried)、难过(sad)、持旗(flag)

实测换参考不增加耗时(见下表),补多少段都不影响速度。

### 延迟:引擎这边每句约 1.7 秒到底,剩下的杠杆是并发

2026-09-24 下午在 5090 上实测(空闲,64 步,阿米娅,`batch_size` 20 = 现在的做法,每项取两次里快的):

| 测什么 | 出第一段声音 | 全部合成完 |
|---|---|---|
| 中等句(27 字,约 6 秒音频) | 1.74 秒 | 1.74 秒 |
| 只合成它的首段「博士,您回来了。」 | 1.49 秒 | 1.49 秒 |
| 中等句,分段返回(`streaming_mode=1`),每批 1 段 | 2.64 秒 | 6.27 秒 |
| 长句(51 字,约 10 秒音频) | 1.82 秒 | 1.82 秒 |
| 长句,分段返回,每批 1 段 / 2 段 | 1.32 / 3.04 秒 | 10.91 / 5.94 秒 |
| 每次都换一段参考 vs 一直用同一段 | — | 1.77 vs 1.74 秒 |

结论:
- 每句合成时间基本固定在 1.5–1.8 秒,和长短关系不大(主要是 64 步本身的开销)。长句约 0.18 倍实时
- v4 模型**不支持真流式**:`TTS.py` 里 v3/v4 开流式会自动退回「分段返回」。首段单独合成只快 0.25 秒,分段返回更慢。这两条路排除
- 降到 32 步能快一些,但用户试听选的是 64 步,不降

前端节奏这边,用户已经自己改过:「翻页停语音」可以关(上一句接着念,直到这句的语音开始)、不等语音时文字后面转圈、自动播放等这句念完再翻(`vn/vnSettings.ts` 的 `voiceInterrupt`、`autoWaitVoice`)。

剩下的问题:翻页快于每句 1.8 秒时会追上;已经发出去的请求取消不掉,跳过的那句会挡着当前句 1.8 秒。服务端同一时刻只处理一个请求,所以要**在同一张 5090 上开多个 api_v2 实例,并发合成**。

## 已确认的决策

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| 1 | 怎么并发 | 同一张卡上开 N 个 api_v2,各占一个端口 | api_v2 一个进程同一时刻只处理一个请求;显存 32 GB,一个实例约 3–4 GB |
| 2 | 实例在界面上怎么填 | 一个语音服务填多个地址(一行一个);另有「按端口连续生成」快捷填法 | 用户要两种都有。存储只有一份地址列表,快捷填法只是帮忙生成这几行 |
| 3 | 存哪 | `tts_connections.options["urls"]`,`base_url` 同步存第一个 | `options` 是预留的 JSON 列,不用写迁移脚本;老数据没有 `urls` 就当 `[base_url]` |
| 4 | 谁分配请求 | 后端调度器,按「同权重优先、空闲优先」 | 多角色时每个角色基本固定在一个实例上,不来回切权重(每次 2 秒);单角色时几个实例一起合成后面的句子 |
| 5 | 前端同时发几个 | 这张卡用到的实例总数 | 当前句优先的规则不变,有空位就先发当前句;跳过的那句还在合成时,当前句能用别的实例 |
| 6 | 先测再做 | 计划第一步实测;2 个实例比 1 个快不到 30% 就停 | 并发的收益取决于 GPU 同时跑两个进程时能快多少,现在不知道 |

## 第一步:实测

等台式机在线、没在打游戏时做。用临时端口(9881、9882……)和配置副本,不碰 9880 和 `tts_infer.yaml`,测完结束进程、删掉副本。

- 测 1、2、3 个实例:每个实例加载同一套阿米娅权重,用 6 句不同的中等句(20–30 字),按实例数同时发,记总耗时、每句耗时,以及显存总量的变化
- 吞吐 = 句数 / 总耗时
- **判断**:
  - 2 个实例的吞吐 ≥ 1 个的 1.3 倍 → 写代码。实例数取「再加一个,吞吐提升不到 15%」之前的那个数,最多 3 个;5090 的启动脚本和 AnimaVN 里语音服务的地址列表都按这个数配
  - 不到 1.3 倍 → 停下来和用户商量,不写代码。这时多实例只剩多角色场景下省掉切权重的 2 秒,可能不值得多占这份显存、多一层复杂度
- 结果记进 `docs/voice-server.md`

### 结果(2026-09-24,5090 空闲,64 步,`batch_size` 20,阿米娅)

6 句不同的中等句,共 32.9 秒音频;每种实例数跑 3 轮取最快:

| 实例数 | 总耗时 | 单句平均 / 最长 | 吞吐 | 相对 1 个 |
|---|---|---|---|---|
| 1 | 10.22 秒 | 1.70 / 1.92 秒 | 0.59 句/秒 | 1.00× |
| 2 | 9.26 秒 | 2.94 / 3.70 秒 | 0.65 句/秒 | 1.10× |
| 3 | 9.78 秒 | 4.78 / 5.53 秒 | 0.61 句/秒 | 1.05× |

- 多开实例几乎不涨吞吐,单句反而变慢。之后在台式机上测清楚了:声学部分每步都在固定 1000 帧上跑 DiT,GPU 利用率 89%、功耗 462 W,一个实例就已经把 GPU 占满了。见 `docs/voice-server.md` 的「为什么每句要 1.7 秒」
- 显存:每个实例加载完约 2.8 GB,合成过后约 3.5 GB
- 结论:不达标,不写代码。「跳过的那句挡着当前句」这个问题,多实例也解决不了:两句同时合成,每句都要 2.9 秒左右,和排队差不多

## 结构

后端:
- `app/tts/pool.py`(新)—— `WorkerPool`:一个语音服务的一组 worker,负责选实例、失败冷却、换实例重试、并发预热和测试。不关心是哪家引擎,worker 只要满足 `TTSEngine` 协议
- `app/tts/gpt_sovits.py` —— 基本不动。一个 `GptSovitsEngine` 就是一个 worker(一个地址),锁、记住的权重、预热状态都在它身上
- `app/tts/registry.py` —— 从「连接 → 一个引擎」改成「连接 → 一个 `WorkerPool`」。签名 `(api_type, 地址列表, sample_steps)` 变了就整组重建
- `app/api/tts.py` —— 语音服务的增删改查换成 `urls`;测试、预热按实例返回结果;合成的响应头加 `X-TTS-Worker`;读地址统一用 `connection_urls(conn)`
- `app/schemas.py`、`app/main.py`(CORS 的 `expose_headers` 加 `X-TTS-Worker`)

前端(`frontend/src/debug/`):
- `lib/api.ts` —— 语音服务类型的 `base_url` 换成 `urls`;测试、预热的返回带每个实例的结果;`speak()` 多读一个 `X-TTS-Worker`
- `components/VoicePanel.tsx` —— 多行地址栏、「按端口连续生成」、按实例列出测试 / 预热结果
- `vn/voice.ts` —— 播放器从「同时 1 个请求」改成「同时最多 n 个」,`setConcurrency(n)`
- `vn/VNScreen.tsx` —— 算出 n 交给播放器;控制台的语音表加一列「实例」

## 数据

- `tts_connections.options["urls"]`:地址列表,顺序就是实例编号(从 1 开始显示)。`base_url` 同步存 `urls[0]`
- `connection_urls(conn)`:`options` 里有非空的 `urls` 就用它,否则 `[base_url]`
- 校验:去掉首尾空白和末尾的 `/`;必须是 `http://` 或 `https://` 开头;不能重复;1–8 个。不合格返回 400,说明是第几行、什么问题

## 调度规则

`WorkerPool` 给每个 worker 记三样东西(都在事件循环里改,选实例和登记之间没有 `await`,不用额外加锁):
- `pending`:派给它、还没结束的请求数(含正在合成的)
- `assigned`:最后一个派给它的请求用的权重 `(gpt_weights, sovits_weights)`。它排队的请求跑完后加载的就是这套,所以按它判断「同权重」,而不是按当前加载的
- `down_until`:冷却到什么时候;在这之前不派请求

选实例(只在没冷却的里面选;全部都在冷却就不排除任何一个,不然服务恢复了也不会再试):
1. 空闲(`pending == 0`)且 `assigned` 和这句的权重相同 → 选它
2. 空闲 → 选编号最小的
3. 都忙:`assigned` 相同的里面选 `pending` 最少的;没有相同的就在全部里面选 `pending` 最少的。一样多就选编号小的

预热成功后也把 `assigned` 设成这套权重。

## 出错

| 情况 | 处理 |
|---|---|
| 连不上(worker 抛 503) | 这个实例冷却 30 秒,在没试过的实例里按上面的规则再选一个重试这句(没冷却的优先);都试过了才返回 503「连不上语音服务(N 个实例都连不上)」 |
| 超时(504) | 不重试,直接返回。换实例重来只会让玩家多等一轮 |
| api_v2 报错(502) | 不重试。参考音频不存在、只有标点这类问题换哪个实例都一样 |
| 合成成功 | 这个实例的冷却清零 |

只有一个实例时,行为和报错文案都和现在一样(503 仍是「连不上语音服务 <地址>」)。

## 接口

- `GET /api/tts/connections`、`POST`、`PUT`:`base_url` 换成 `urls: list[str]`
- `POST /api/tts/connections/{id}/test` → `{ms, workers: [{url, ok, ms, error}]}`。所有实例都失败才返回错误状态码(用第一个的状态码和说明);部分失败返回 200,由界面标出哪几个不通
- `POST /api/tts/warmup {profile_id, force}` → `{ms, workers: [...]}`,所有实例同时预热(每个实例第一次合成要 30–40 秒,只预热一个的话,别的实例第一次接活会卡很久)。成败规则同上
- `POST /api/tts/speak`:响应头加 `X-TTS-Worker`(实例编号,从 1 开始);命中缓存时没有这个头
- 缓存键不变(里面没有地址),哪个实例合成的都能命中

## 前端

### 语音页

- 地址栏改成多行文本框,一行一个实例
- 「按端口连续生成」:填实例数(1–8),点一下,用第一行的地址,端口从它开始往上数,把文本框整个换成这几行。第一行没写端口就提示「第一行要带端口,比如 http://127.0.0.1:9880」
- 测试、预热的结果按实例一行一行列:地址、通 / 不通、耗时、报错原文

### 播放器

- `busy: boolean` 换成 `inflight: number`;`pump()` 在 `inflight < concurrency` 时继续从队首取请求发出去
- 队列顺序的规则不变:当前句在最前,玩家点的重播 / 重新生成插在最前
- `setConcurrency(n)`:n 变小时已经发出去的照常完成,只是不再多发
- `ClipState` 的 `ready` 多一个 `worker: number | null`(命中缓存是 null)

### n 怎么算

这张卡绑定的声音(主声音 + 其他声音)用到的语音服务,地址数相加,同一个服务只算一次,最少 1。

## 5090 部署

- `D:\GPT-SoVITS\start-api.bat` 改成按端口列表拉起多个实例:每个端口的配置是 `GPT_SoVITS\configs\tts_infer_<端口>.yaml`,没有就从 `tts_infer.yaml` 复制一份;每个实例单独开一个窗口
- **每个实例必须用自己的配置文件**:切权重时 api_v2 会把路径写回配置文件,共用一份会互相覆盖
- 重启后每个实例默认加载的是它自己最后切过的那套权重。AnimaVN 的调度器按自己记的状态判断,和以前单实例一样,手动切过权重后点一次「预热」(`force`)纠正
- 装好 Tailscale 后,防火墙对这一段端口只放行 100.64.0.0/10

## 测试

后端(pytest,沿用 `tests/conftest.py` 的 `FakeGsv`,每个地址起一个假实例):
- 调度:空闲且同权重的优先;都忙时排到同权重、队最短的那个;没有同权重时选队最短的
- 两个请求同时来、有两个空闲实例时,真的同时发到两个实例(不是排队)
- 一个实例连不上:冷却、换实例重试成功;冷却期内不再派给它;全部连不上才返回 503
- 504、502 不重试
- 预热、测试:部分失败返回 200 并带每个实例的结果;全部失败返回错误
- 老数据只有 `base_url`、`options` 里没有 `urls` 时照常工作
- 地址校验:格式、重复、个数
- 缓存命中时不请求任何实例

前端没有测试框架:验证靠 `npm run build`、`npm run lint`,以及浏览器里实际跑一遍(两个实例,阿米娅、琴柳各一张卡;快速连点、跳过、重播、停掉一个实例)。

## 没做 / 之后再聊

- 流式时首句也等语音、按「在听还是在扫」自动决定等不等:用户已经用「翻页停语音」「不等语音 + 转圈」这组设置解决,先不做
- 已知的小问题:在菜单里把「翻页停语音」从关改成开时,当前这句会从头再念一遍(`useVoiceLine` 换句的 effect 依赖了 `interrupt`)
- 降采样步数、分段返回:实测不划算,见背景
- 多台机器:地址列表天然支持,但这次只测同一张 5090
- 在配置里把角色固定到某个实例:调度器按权重自动分配,不需要
